# Day 12 — Agent 1: MCP Server Health Monitor

## Security thread
**Tool-surface design as least privilege.** An MCP server does not give a model a
shell — it gives the model *exactly* the capabilities you define, with the
argument schema you specify. Designing that surface is the same discipline as
writing a sudoers rule: grant one capability, deny everything else by omission.

---

## 1. What an MCP server actually is

A language model can reason about a host but cannot look at it. The naïve fix —
give the model shell access — is unacceptable. **MCP (Model Context Protocol)** is
the standard for the bounded alternative: a small program you write that exposes
named, typed **tools**, and nothing else.

**Where it lives and how it runs — the non-obvious part:**

| | nginx / http.server | This MCP server |
|---|---|---|
| Process model | Long-running **daemon** | **Inert file** until launched |
| Transport | TCP port, listening socket | **stdio** (stdin/stdout pipes) |
| Lifetime | Until stopped | Exactly the client session |
| Reachable by others | Yes, if the port is open | **No — nothing is listening** |

`claude mcp add` writes a registration into `~/.claude.json`. When a session starts
in that directory, Claude Code **spawns `server.py` as a child process** and speaks
JSON-RPC over its pipes. Verified empirically: `ps aux | grep server.py` returns
nothing before the session, shows the process with Claude Code as PPID during it,
and returns nothing after.

> **stdio transport is the safest default: a server that is not listening on
> anything cannot be reached by anyone.** HTTP transport opens a port and
> immediately raises "who else can reach it?"

## 2. Tool-surface design (decided before writing code)

### Which tools belong?
| Candidate | Verdict | Reasoning |
|---|---|---|
| `run_command` | **Never** | That *is* a shell — precisely what MCP exists to avoid. Prompt injection in any content the model reads becomes command execution on the host. |
| `fix_finding` | **Not in v1** | A **write** capability. A model that misreads a finding makes an unauthorised change to a live host. Remediation belongs behind human approval, or on a separate server with its own consent step. Read and write are different privileges and get granted separately (Day 2). |
| `run_audit` | **Yes** | Read-only, deterministic, no steerable arguments. |

### What arguments?
**None.** Not a path, not a check name, not a filter. If a free-form argument
reached the shell script, that is command injection — the model (or anything
influencing it) supplies `"; rm -rf /"`. If filtering were ever needed, it must be
validated against a hardcoded allowlist of known IDs.

> Day 5's rule, restated: **keep untrusted input in the data position, never the
> code position.**

### Observe or change?
**Observe only.** The architectural principle for all five agents in this
programme:

> **Evidence is generated by deterministic tooling and interpreted by a model —
> never the reverse.**

The moment a model can change state, the question shifts from "is this report
accurate?" to "what did it do?", which needs a far stronger authorisation story.

## 3. Architecture — three files, three responsibilities

| File | Owner | Runs as | Responsibility |
|---|---|---|---|
| `/usr/local/bin/cis-audit-json.sh` | `root:root` 755 | **root** | *What to look at* — 11 checks, pure observation |
| `/etc/sudoers.d/cis-audit` | `root:root` 440 | — | *The privilege boundary* |
| `server.py` | user | **unprivileged** | *What it means* + the MCP interface |

### The privilege boundary
```
bassam ALL=(root) NOPASSWD: /usr/local/bin/cis-audit-json.sh
```
Several checks require root (`/etc/shadow`, `ufw status`, `find /`). The
alternatives were: drop those checks (loses the valuable ones), run the whole
server as root (hands the agent full system privilege), or **grant NOPASSWD on
exactly one root-owned script**.

**The asymmetry is what makes this safe:** the script is `root:root 755` — the
user can *execute* it but cannot *modify* it. Were it user-writable, this sudoers
rule would be a privilege-escalation primitive: edit the script, run it via sudo,
execute anything as root. **A root-executed script writable by a non-root user is
always a finding.**

### Deliberately dumb output
The bash layer emits opaque IDs only:
```
no-rogue-suid|FAIL|/home/bassam/.cache/backup-helper;
```
No title, no severity, no rationale. All meaning is attached afterwards by
`CHECK_META`, a dict **in Python source**. **Even a compromised audit script could
not inject a false rationale or downgrade a severity.**

### No shell, anywhere
```python
subprocess.run(["sudo", "-n", AUDIT_SCRIPT], capture_output=True, text=True, ...)
```
List form, never `shell=True`. Arguments pass directly to `execve`, so no shell
parses them and there is no injection surface.

### Scope humility encoded in the data
`AuditReport.scope_note` is part of the returned structure:
> *"SUBSET of the CIS Ubuntu benchmark, not full compliance. A perfect score means
> this host passed the checks that were selected, not that it is secure."*

The Day-11 lesson is encoded where the model cannot omit it — and in the demo it
was correctly reproduced in the final caveat.

## 4. Acceptance evidence

Three misconfigurations seeded, all detected:
```
no-ww-files|FAIL|/opt/maintenance.sh;
no-rogue-suid|FAIL|/home/bassam/.cache/backup-helper;
no-nopasswd-all|FAIL|/etc/sudoers.d/99-deploy-bad;
```

`claude mcp list` → `health-monitor: ... ✔ Connected`

### The model's reasoning (the part worth studying)
Asked to audit the host and rank failures, Claude Code called `run_audit` (did not
shell out) and returned **8/11 passed, 3 failed**, then went beyond the data:

- **Re-ranked by realistic exploitability, not by severity label.** All three
  failures carried `severity: high`, but it ordered them: SUID first (needs only
  local execute access), sudoers second (widens to CI/automation credentials),
  world-writable third — *"execution-dependent: an attacker has to know or wait
  for something to run it."* That judgement was not in the input.
- **Surfaced a second-order risk not encoded anywhere:** if the *directory*
  containing the SUID binary is writable, an attacker can replace the binary and
  it remains SUID-root.
- **Honoured the scope note** in its closing caveat.

**Division of labour confirmed:** nothing about the host's state was invented;
everything about prioritisation and impact was reasoned. Deterministic evidence,
model interpretation.

### A check validating a rule added for itself
`no-nopasswd-all` continued to **PASS** after adding the agent's own sudoers grant,
because it matches `NOPASSWD:` followed by `ALL` — distinguishing a **scoped**
grant (one command, acceptable) from a **blanket** one (a finding). A check unable
to tell those apart would be useless.

## 5. Environment issues resolved
- **PEP 668 `externally-managed-environment`** — Debian/Ubuntu now refuse
  system-wide `pip` installs because pip and apt both manage `/usr/lib/python3`.
  A venv is the sanctioned path, not optional hygiene. (`--break-system-packages`
  exists; the name is the warning.)
- **`python3-venv` is a separate package** on Ubuntu and must be installed before
  `python3 -m venv` works.
- **SDK version pinned** `mcp[cli]>=1.27,<2` → installed **1.29.0**. The SDK is
  mid-transition to v2; its own guidance is to hold a `<2` upper bound until
  migration. **An unpinned major-version bump silently breaks working code.**
- **Suppressed output hid a failure.** A previous `apt install -y openssh-server
  2>/dev/null >/dev/null` concealed a failing post-install script, leaving dpkg
  stuck and every later install reporting an error. Resolved by purging the
  package (the sshd config artifact had already been syntax-validated).
  **Day 5's lesson, re-learned: suppressing output hides failures.**

## SOC 2 mapping
| Control | Criterion |
|---|---|
| Single read-only tool; no shell, no write capability | **CC6.1** (least privilege applied to an automated agent) |
| Scoped NOPASSWD on one immutable root-owned script | **CC6.1** |
| Automated, repeatable configuration audit with per-check evidence | **CC7.1** (detecting configuration drift) |
| Findings mapped to CIS items and TSC controls | **CC4.1** (control monitoring and evaluation) |
| Timestamped structured output suitable for an evidence pack | **CC7.2** |

## Adwen service mapping
An agent producing a timestamped, control-mapped host audit — and drafting the
findings section — is the **hardening review** engagement with the manual
collection removed. Agents 2 (IaC review) and 5 (compliance evidence) are the same
play in other domains.
